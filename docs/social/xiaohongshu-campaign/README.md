## 01｜我受够了 AI 干完活只回一句「好了」

素材目录：[`../../images/social/01-visible-work`](../../images/social/01-visible-work)

### 标题候选

1. 我受够了 AI 干完活只回一句「好了」
2. 开源了：把 AI 干活的过程完整摊开
3. 做了个多 Agent 工程工作台，不想再猜它改了啥

首发建议用标题 1。它先说真实挫败感，产品名留到正文，不会像广告标题。

### 正文

做 AI 编程工具越久，我越不在意它能不能一口气写很多代码。

真正让我不放心的是：任务一长，Plan 在哪、谁改了文件、命令到底跑没跑、测试是不是真的通过，最后常常只剩一句「完成了」。

所以我做了 Threadlight。

它不是把几个聊天窗口并排，而是把多 Agent 协作做成 Runtime 行为：每个子 Agent 有持续线程；写工作区时只有一个所有者；对话、Agent 树和模型状态都可以恢复。

同一条任务时间线上，可以直接看到：

1. Plan：它准备怎么做
2. Agent：任务分给了谁
3. Tool / Terminal：实际运行了什么
4. Files / Diff：真正改了哪些内容
5. Delivery：最后交付和验证结果

目前有 macOS 桌面端、Web 客户端和可自部署的 Host。核心保持 Provider-neutral，不把某家模型的协议写死在 Agent Loop 里。

项目已经按 Apache-2.0 开源：`threadlight.xyz`，GitHub 搜 `nagisa77/threadlight`。

先说清楚边界：它不是安全沙箱，内置工具使用当前用户权限；放到重要环境之前，仍然需要自己评估权限和隔离。

如果你也在做长任务 Agent，你最想先解决哪一个问题：过程不可见、任务不可恢复，还是多个 Agent 同时乱改？

#AI编程 #开源项目 #多Agent #AIAgent #独立开发 #开发者工具 #VibeCoding

### 置顶评论

项目地址：`github.com/nagisa77/threadlight`。官网有架构图、自部署命令和完整 Showcase。macOS 安装包目前没有 Apple 签名，第一次打开请按 README 的说明操作；介意这一点可以直接使用 Web + 自部署 Host。

### 常见评论回复

- **支持 Windows 吗？** 现在没有原生 Windows 桌面端；Web 客户端可以连接自部署 Host。
- **只能用某一家模型吗？** Agent Loop 本身是 Provider-neutral 的，供应商协议放在 adapter；仓库里已经有 OpenAI 与兼容接口的接入说明。
- **和同时开几个终端有什么区别？** 重点不是窗口数量，而是持续子线程、写入所有权、工具证据和恢复状态都由 Runtime 管理。

## 02｜让 AI 改大项目，我只看这 5 类证据

素材目录：[`../../images/social/02-five-signals`](../../images/social/02-five-signals)

### 标题候选

1. 让 AI 改大项目，我只看这 5 类证据
2. 别只看 AI 说「完成了」：我的 Agent 验收清单
3. AI 写代码到底靠不靠谱？先看这 5 个地方

首发建议用标题 1。信息密度高，收藏意图明确，也没有夸张承诺。

### 正文

我现在验收 Coding Agent，不会先看最后那段总结。

跨文件、长时间、多个 Agent 一起做的任务，我按顺序看这 5 类证据：

**01｜Plan**  
它有没有把目标、约束、验证方式拆清楚？如果第一步就含糊，后面跑得越快越危险。

**02｜Ownership**  
并行任务有没有明确的写入所有者？不是「大家尽量别冲突」，而是 Runtime 真的知道谁能改工作区。

**03｜Tool Output**  
命令是真的执行了，还是总结里说「已经运行」？我会看命令、输出、错误和耗时。

**04｜Files & Diff**  
最终答案不重要，真实变更才重要。改了哪些文件、删了什么、有没有越界，一眼要能复核。

**05｜Recovery**  
长任务最容易漏掉的证据。中断之后，对话、Agent 树、工具调用和模型状态能不能继续，而不是从头猜。

这不代表所有小改动都要走重流程。修一句文案当然没必要；但任务越长、改动越广、并行越多，缺少证据的风险就越高。

我把这套检查做进了 Threadlight：Plan → Agent → Tool → Diff → Recovery，放在同一条任务线上。项目已开源，官网和仓库里都有完整架构与自部署方式。

先收藏，下次让 AI 改大项目时照着过一遍。你会给这张清单补第 6 条什么？

#AI编程 #CodingAgent #开发效率 #程序员 #开源项目 #工作流 #VibeCoding

### 置顶评论

这套清单更适合「长任务 / 多文件 / 多 Agent」，不是为了把每个小改动都流程化。Threadlight 项目地址：`github.com/nagisa77/threadlight`；第 5 条恢复能力在 README 的架构部分有说明。

### 常见评论回复

- **是不是看 git diff 就够了？** Diff 只能说明最终改动，不能替代任务拆分、运行证据和中断后的状态恢复。
- **多 Agent 一定比单 Agent 好吗？** 不一定。能清楚拆分、并行收益高时才值得；小任务增加 Agent 反而会增加协调成本。
- **为什么强调模型状态？** 很多供应商会返回需要在下一轮原样带回的 opaque state；丢掉它，推理和工具调用链可能断开。

## 03｜一句需求，Agent 做出了事故回放沙盘

素材目录：[`../../images/social/03-incident-replay`](../../images/social/03-incident-replay)

### 标题候选

1. 一句需求，Agent 做出了事故回放沙盘
2. 没给设计稿，它从零做了个事故模拟器
3. 多 Agent 从零做项目，过程比结果更值得看

首发建议用标题 1。图 2 会原样展示输入，不需要用夸张形容词制造神秘感。

### 正文

我给 Threadlight 的需求只有这一段：

「从零创建 incident-replay-lab：制作可播放的电商线上事故沙盘，包含服务拓扑、实时指标、事件流、时间轴和自动复盘。」

没有准备项目骨架，也没有逐页 UI 说明。

它先拆任务，再逐步实现、运行和修正。最终结果里有：

- 可以点选的服务拓扑
- 延迟、错误率等三通道指标
- 跟随时间推进的事件流
- 可以播放和定位的事故时间轴
- 自动生成的复盘摘要

这里必须说明：它是一个确定性的本地事故模拟器，展示的是模拟数据，不是真实公司的线上故障，也不是接入了生产监控。

我更在意的不是「一次抽中好结果」，而是过程能不能被复盘：谁接了任务、跑过什么命令、改了哪些文件、测试结果是什么，都留在同一条任务时间线上。

Threadlight 现在已经开源，官网放了这个案例和另外两个完整结果。你想看它下一次从零做什么？我会从评论里挑一个边界清楚、能公开验证的需求继续跑。

#AI编程 #AIAgent #开源项目 #独立开发 #前端开发 #事故复盘 #VibeCoding

### 置顶评论

案例输入、过程截图和最终结果都在这组图里；官网 `threadlight.xyz` 还有大图。模拟器使用确定性本地数据，不对应任何真实业务事故。项目仓库：`github.com/nagisa77/threadlight`。

### 常见评论回复

- **这是直接生成一张 UI 图吗？** 不是。案例包含可运行实现、真实文件变更和验证过程，图 3 展示任务过程，图 4 才是结果。
- **数据是真的吗？** 是确定性的模拟数据，目的是演示事故时间线和复盘交互，不冒充真实生产指标。
- **为什么不给更长的 Prompt？** 这个案例想验证从需求拆分到交付的完整链路；真实业务仍然应该提供约束、数据口径和验收标准。
